## 3.3 性能测试

TriGuard由管理员网站、用户浏览器插件、业务服务和三个计算方组成。用户通过插件完成口令检查、登录与修改，管理员通过网站查看受保护统计并设置口令要求。因此，系统的工程性能既取决于常用操作的响应时间，也受到三方统计计算与账户数据存储开销的影响。本作品在保留秘密分享、加密通信、签名核验和事务恢复机制的基础上，采用计算结果复用与无损数据压缩降低运行开销，并从时间开销和存储开销两个方面进行测试。

### 3.3.1 时间开销

登录、口令检查和改密是用户直接参与的操作，其执行时间会影响使用体验；群体统计则需要处理多个账户的秘密输入，计算开销相对较大。为减少运行开销，本作品采用精确分块比较复用口令匹配结果，仅秘密选取所需的热门项，避免对全部候选进行完整排序；同时复用字符类型和连续序列检查的中间结果，并省去登录、检查过程中整份账户状态的复制与无变化写回。

本作品依据实际使用场景开展以下测试：

1. 在100个合成账户的站点中，分别对登录、私密口令检查和改密进行预热后的5次测量。计时从客户端发起操作开始，覆盖策略与版本读取、请求签发、份额生成与提交、三方计算、回执核验和业务完成，采用中位数表示典型耗时。
2. 在10个合成账户的站点中，对不同数据快照进行3次全量统计发布。每次均由三个计算方处理普通逐账户秘密份额，发布结构人数、结构内匿名热门频次及18类规则人数统计，单次隐私预算为0.5，采用3次测量的中位数表示统计发布耗时。

实验在同一台机器上运行三个独立计算进程，通过HTTPS完成业务交互。各次统计发布均实际执行秘密计算与加噪过程。测试结果如下表所示。

| 操作 | 中位耗时 / 秒 |
| --- | ---: |
| 用户登录 | 0.927 |
| 私密口令检查 | 1.761 |
| 用户改密 | 1.928  |

结果表明，在本机测试条件下，三项用户交互操作的中位耗时均低于2秒，能够以秒级响应完成私密认证、规则检查和凭据更新，时间开销较小。


### 3.3.2 存储开销

除执行时间外，账户增加所带来的存储增长也是影响系统实用性的重要因素。TriGuard在业务服务中保存账户版本、策略和任务等信息，三个计算方分别保存本方的口令份额。大量数字份额与重复字段会增加数据库容量。为降低存储开销，本作品对大型持久化记录采用带版本标识的无损压缩，写入数据库后在读取时恢复原始数据，同时保留对旧格式的兼容性。

实验分别设置10、25、50、100、200、500、1,000和5,000个合成账户。每个账户均采用64字符填充的普通秘密份额，将账户数据写入系统采用的SQLite数据库，再逐项读回核对。存储量统计业务数据库与三个计算方数据库的物理页总量，以下列出三个代表性规模的结果。

| 账户数量 | 数据库总量 / MiB |
| ---: | ---: |
| 100 | 0.355 |
| 1,000 | 2.969 |
| 5,000 | 14.645 |

数据库存储量随账户规模的变化如图所示。在本次测试中，存储量随账户数量增加近似线性增长，5,000个账户的数据库总量为14.645 MiB。全部测试记录均通过写入与读回一致性核验，压缩未改变秘密份额及账户数据的内容。

用户端和管理员端的构建文件也较为精简：当前浏览器插件构建文件总量约为0.266 MiB，管理员网页构建文件总量约为0.271 MiB。这两项为前端文件容量；上述数据库测量则仅反映账户初始化后的数据存储，不包含程序依赖、证书、运行日志及后续审计历史，因而不等同于整套系统的安装容量。

本节测试说明，TriGuard能够通过减少重复计算、避免不必要的状态写入和无损压缩降低工程开销，并在本机小样本条件下完成秒级用户交互。
