# 分批注册动态口令策略：文献与重设计建议

核查日期：2026-10-10。本文只讨论**新用户注册时**的策略调整；存量账户通知改密是项目的另一条实验线。以下是定向检索和当前代码审阅，不是穷尽的系统综述。文献链接指向原论文或出版方页面；“建议”是本项目的研究设计，尚无新增实验结果。

## 直接相关的研究

| 工作 | 注册阶段的做法 | 对本项目的启发与边界 |
| --- | --- | --- |
| [Schechter 等，*Popularity Is Everything*，2010](https://www.usenix.org/conference/hotsec10/popularity-everything-new-approach-protecting-passwords-statistical-guessing) | 随注册更新口令流行度，对已过热的完整字符串拒绝注册；用近似计数结构避免保留明文计数表。 | “在线热门口令拦截”已有先例，可作为必须击败的动态基线。 |
| [Malone 与 Maher，*Investigating the Distribution of Password Choices*，2012](https://mural.maynoothuniversity.ie/id/eprint/3754/1/DM_Password_Choices.pdf) | 在线估计用户提议的口令频率，用概率性拒绝机制使最终分布更均匀，并在 RockYou 抽样模拟。 | 适合作为分布均匀化基线；需要同时计入重复提议次数和重选行为。 |
| [Blocki 等，*Optimizing Password Composition Policies*，2013](https://arxiv.org/abs/1302.5101) | 建模用户偏好顺序、规则允许集合及其诱导的口令分布，优化最热门口令或前 $k$ 个口令的质量。 | 提醒我们：规则本身的强弱不能替代**实际诱导分布**和多个猜测预算下的结果。 |
| [Segreti 等，*Diversify to Survive*，2017](https://www.usenix.org/system/files/conference/soups2017/soups2017-segreti.pdf) | 比较按使用量禁用完整字符串或字符类别结构的自适应策略，并在 2,619 人实验中测安全与可用性。 | 结构频率阈值和反馈提示值得加入；论文测过真实用户，因此我们的固定响应模拟不能声称验证可用性。 |
| [Yang 等，*DPPG*，2018](https://nesa.zju.edu.cn/download/DPPG%20A%20Dynamic%20Password%20Policy%20Generation%20System.pdf) | 从当前库内口令特征频率生成新用户规则，设置探索与利用模式，使结构等特征更分散。 | “根据已有分布给新用户生成不同规则”已有直接先例；项目不能把这一点当作首创。 |
| [Johnson 等，*Skeptic*，2020](https://arxiv.org/html/2007.03809v2) | 在真实频次分布上过滤候选策略，并用不同用户重选假设重新分配概率质量，再选择诱导分布更均匀的规则。 | 用户响应假设必须做敏感性分析；可以将它作为强的**开发集预选固定规则**对照。 |
| [Tan 等，*Practical Recommendations for Stronger, More Usable Passwords*，2020](https://users.ece.cmu.edu/~lbauer/papers/2020/pwd-guidance-ccs20.pdf) | 对比黑名单与最低猜测强度要求，研究创建阶段的安全与可用性。 | 提供“按猜测强度设门槛”的策略家族，不必局限于长度和字符类别。 |
| [Xiao 与 Zeng，*Dynamically Generate Password Policy via Zipf Distribution*，2022](https://ieeexplore.ieee.org/abstract/document/9715109) | HTPG 按 Zipf 头尾和特征信息增益生成改进建议，周期性重算整体分布。 | 是分布引导规则的近邻；主要用于头部口令改进，不能把它的改密模拟直接视作新用户注册实验。项目已有本地论文和复现审计。 |

[NIST SP 800-63B-4（2025）](https://pages.nist.gov/800-63-4/sp800-63b.html)对实践路线另有约束：单因素口令最低 15 字符、多因素场景可最低 8 字符；要求检查常见或泄露口令，反对额外字符类别规则，并要求给被拒用户解释原因。因此，项目里的“长度 8”和类别规则可保留为**历史或机制对照**，不能直接作为当前通用部署建议。

## 推荐的研究问题

**给定相同的注册用户、用户负担上限和训练信息，利用已经注册用户的分布反馈，是否能在未来用户偏好变化时，比事先选好的固定策略降低终态猜测命中率？这种收益是否在不同用户响应假设和攻击模型下仍成立？**

注册模拟的状态转移应明确写为：第 $t$ 批前已有 $N_t$ 个账户，分布为 $p_t$；下一批在策略 $a_t$ 下产生 $m_t$ 个最终口令，分布为 $q_t(\cdot\mid a_t)$，则

$$
p_{t+1}=\frac{N_t p_t+m_t q_t(\cdot\mid a_t)}{N_t+m_t}.
$$

过去账户不会因新注册规则自动改密。这个式子使“新批改善”和“累计库改善”分开，也说明只看下一批碰撞率可能错过终态风险。

## 一条可落地的重设计路线

1. **把动作从网站标签改成可解释机制。** 在同一基础规则之上实现：固定泄露口令黑名单、按当前完整字符串频率设上限、按字符类别结构频率设上限、按冻结开发攻击模型的估计猜测预算设最低强度，以及“保持当前规则”。每类动作的阈值和更新周期都写入配置。网站规则仍作现实参照，不承担主优化空间。先做完整字符串频率和结构频率两类，避免候选膨胀。
2. **保留当前流水线，替换策略决策层。** 复用抽样、逐用户记录和 F/A0/A1 评价；把 `dynamic_controller.py` 的选择目标从单一碰撞率改为“预测 A1 风险代理 + 用户成本约束”，同时保存碰撞率作为独立指标。代理可先用开发数据上的 Top-$B$ 质量和冻结攻击模型命中，之后核查它与最终 A1 的相关及失配。只用已结束批次和预先分出的开发资料决策，未来批次与终态测试集绝不参与选动作。
3. **设置等负担的强对照。** 至少包括无策略、固定 Google、在开发集上选出的最佳固定机制、固定阈值黑名单、动态流行度阈值、动态结构阈值、随机更新和所提控制器。所有方法用同一批原始用户与配对随机响应；既报告相同约束下的结果，也画实际修改率或重试次数对 A1 命中率的 Pareto 图。额外的“知道未来后才选择”的策略只能当不可部署的上界。
4. **制造清楚标记的分布变化，再检验在线反馈。** 主实验先用当前随机顺序作为平稳场景，承认固定策略可能胜出；扩展实验设置预注册的混合分布变化，例如后半程从另一独立来源或不同结构子群抽样。若暂时只有 RockYou，使用从训练部分定义的子群重加权作**合成漂移**，不得称其为真实时间变化。分别测试突变、渐变和无变化；控制器只能从已发生批次发现变化。
5. **把用户响应的不确定性纳入设计。** 现有三种生成方式只是一个场景。另测更常见的尾缀修补、重新选词、口令管理器生成、注册中止及提示是否解释拒绝原因。中止应以独立结果计入完成率，不能悄悄丢出攻击分母。即使缺少新用户研究，也可报告响应权重网格和最差场景边界，不能写成现实采用率。
6. **评价攻击和统计稳健性。** 事先确定 $B=10^2,10^4,10^6$ 等预算，同时报告注册完成率、完成账户中的 A1@预算，以及“每 100 名开始注册者中最终成功注册且在该预算被命中的人数”。这样不会通过丢掉易猜口令来虚增安全表现。辅指标为最热门一猜、Top-$k$ 质量、碰撞率、每人尝试次数、修改率、策略切换次数和模型覆盖率。用多个种子在同一输入上做配对比较；这些轨迹仍是同一源语料下的模拟重复，跨语料验证另列。对蒙特卡洛排名不确定性与未覆盖口令单独报告。

## 优先级与可能的论文贡献

**第一阶段：** 加入动态完整字符串流行度阈值、结构阈值和强静态对照，沿用现有十批、十万人、PCFG 管线。这会直接回答“同成本下动态更新是否有收益”，并与 Schechter、Segreti 对照。若无变化场景中固定策略仍胜出，这同样是可信结果。

**第二阶段：** 加入合成漂移、响应模型敏感性和预测校准。真正可辩护的贡献是说明**什么条件下**历史反馈有用、改善多少、付出多少注册成本，而非宣称首次动态策略。可进一步比较每批更新与每个新用户实时更新的效果与成本。

**第三阶段：** 若能开展经授权的用户研究，再验证拒绝提示、尝试次数、完成率与回忆表现；在此之前只能称为模拟研究。报告中将存量账户局部干预作为第二应用场景，使用同一“分布、攻击、用户成本”评价框架，但不要混为同一个因果实验。

**不建议现在重做整个项目。** 现有数据拆分、响应记录、攻击评价和复核基础很有用；应新建独立的注册机制实验配置与报告，保留 Top15 穷举结果作为诚实的反例。第一阶段完成后，再决定是否值得引入复杂的强化学习或多步规划。
