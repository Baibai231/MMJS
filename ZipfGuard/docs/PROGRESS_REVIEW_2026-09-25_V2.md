# ZipfGuard 第二次详细核查与后续目标

> 核查日期：2026-09-25。正式目录：`MMJS/ZipfGuard`。本文件更新同日第一份进度判断；旧报告中的 7.2 个百分点属于旧协议，不再作为当前成果。

## 一、总体判断

工程底座、论文分布分析、特征计算和实验框架已经建立；上次发现的建议方向、论文权重混用、候选覆盖和部分来源记录问题已有修正。最新结果同时暴露出更根本的问题：当前预算／成本选择器在主实验中不选择任何修改，尚无有效创新结果。

目前最准确的定位是：**具备论文核心方法的研究原型，正在校准复现口径与实验设计；尚未形成经过公平验证的改进算法。**

本次没有重跑全量 RockYou 或完整五种子主实验；对现存报告做了源码哈希核对，并实际运行方向样例、修改目标反例、长尾种子 1 的完整单特征选择诊断，以及全套测试。测试结果见本文末尾的验证记录。

## 三、最新结果应怎样理解

来源：`reports/directed_size900.json`，协议 `robustness-v2`。每个场景五个种子，每次共 900 个合成用户，实际划分为训练 540、验证 180、测试 180。离线猜测预算为 40。候选字符串 114,864，原始合成支持集仍为 652。

### 3.1 全体测试用户的封闭排序结果

安全收益为猜中率的绝对下降，单位是百分点。

| 场景 | 方法 | 安全收益均值 | 修改率均值 |
| --- | --- | ---: | ---: |
| Zipf | 长度＋黑名单 | 7.56 | 26.78% |
| Zipf | 论文 IGR 实现 | 0.00 | 8.33% |
| Zipf | 预算／成本 | 0.00 | 0.00% |
| 长尾 | 长度＋黑名单 | 16.11 | 37.89% |
| 长尾 | 论文 IGR 实现 | 0.00 | 12.89% |
| 长尾 | 预算／成本 | 0.00 | 0.00% |

新方法在上述十次场景运行中均未带来正收益，也没有修改用户口令。论文实现存在修改，但此封闭指标不变。开放 Markov 指标另算：论文臂约为 Zipf +0.11、长尾 +1.00 个百分点；新方法仍为 0，不能把封闭的零收益扩展为所有攻击器都完全无变化。

### 3.2 为什么选择器没有动作

本次独立检查长尾、900 用户、种子 1：

| 单项特征 | 验证集频次攻击收益 | 修改率 | 收益 − 0.25 × 修改率 |
| --- | ---: | ---: | ---: |
| Length | 0 | 12.22% | -0.03056 |
| LSD | 0 | 7.78% | -0.01944 |
| WordType | 0 | 0.56% | -0.00139 |
| Keyboard | 0 | 20.00% | -0.05000 |
| Lastname | 0 | 20.00% | -0.05000 |
| Specplace / Date / Capital | 0 | 0 | 0 |

只接受正分数，最终得到空建议列表。这与当前目标函数一致，不能把“不修改”本身叫作程序故障。它说明当前候选动作、模拟响应与攻击模型组合没有提供可选择的收益。

若所有用户对同一口令都做相同且一一对应的改名，口令频数多重集保持不变；理想的自适应频次排序在同一预算下也就不会获得本质改善。有限样本、排序并列或映射碰撞可能改变具体数字，因此这个机制解释不能替代逐场景验证。

## 四、仍然存在的关键问题

### P0-A：用户响应不对等，影响算法比较

位置：`experiments/robustness_protocol.py` 第 332–339 行；`experiments/suggestion_compare.py` 第 57–66、94–96 行。

现代基线使用按用户 ID 分配的五种后缀；定向长度修改使用固定字符填充。相同输入、20 个合成用户的本次探针中，前者产生 5 种结果，后者产生 1 种。

这意味着对照同时改变了“选择何种策略”和“用户如何响应”。不能把表中现代基线的全部优势单独解释成策略优势，也不能据此宣布 HTPG 理论无效。

**验收目标：**把响应机制作为独立实验因素。所有方法共用响应能力、采用率、随机种子约定和成本模型；同时做确定性响应与多样化响应，报告策略与响应机制的交互。保持黑名单触发范围等算法本身应有的差别。

### P0-B：执行器没有完整满足建议，校验器会误报通过

位置：`experiments/suggestion_compare.py` 第 53–54、69–71、87–91、102–116 行。

本次实际复现三个反例：

| 要求 | 输入与输出 | 问题 |
| --- | --- | --- |
| LSD 变成 `L8` | `abc123` → `abc123!` | 实际变成 `L3D3S1`，未使用目标结构 |
| 使用大写 | `123abc` → `123abc` | 只尝试将第一个字符转大写，输入仍无大写 |
| 避免日期 | `abc2024xyz` → 原字符串 | 提取器识别内部年份，删除器只删除末尾年份 |

三个样例的 `edit_meets_target` 都返回 True。它把“没有修改”直接当成功，且大部分动作默认通过。此外主执行路径未调用该校验器。

**验收目标：**以同一个特征提取器验证修改后条件；返回“成功、已满足、无法执行、发生冲突”四类明确状态；无法执行不得算成功采用；失败不删除用户。LSD、特殊符号位置、词典类与日期类全部覆盖，不能只测长度和字母开头的大写样例。

### P0-C：论文复现口径仍有偏差

- `policy/htpg_generator.py` 第 144、157 行排除了距离相等的样例，但模块说明和输出元数据仍写 `d_head <= d_tail`。需要按论文核定规则，分清忠实版与改进版。
- `experiments/suggestion_compare.py` 的 `_head_model` 使用频次阈值 `>0`，而全量论文拟合使用 `>3`。合成小样本可有独立协议，但不应默认为同一论文口径。
- 类别距离采用众数 0/1 距离，词表采用替代表；完整论文数值复现仍有条件限制。
- 冲突处理主要处理重复特征，尚未充分处理多次修改互相破坏目标。例如长度截断可能破坏前一个日期或结构修改。

**验收目标：**制作“论文公式／算法步骤 → 当前实现 → 差异 → 对结果影响”的逐项表；严格复现版与实验性调整分别命名并独立输出。

### P1-A：候选完整性与实验可追溯性仍不充分

- `directed_coverage` 用有限枚举近似覆盖修改，尚无所有可达两步响应的闭包保证。
- 主报告只保留汇总，难以定位每个种子的动作选择和失败原因。
- 来源清单未覆盖实际使用的 `core/attackers.py`，n-gram 实现变化可能不触发现有表格哈希检查。
- 候选哈希由生成表格脚本事后计算，没有作为原始运行字段存入当前 JSON。
- 当前新报告有来源记录，但旧报告、旧图、旧消融不能混进最新结论。

**验收目标：**运行时保存候选／数据划分哈希、有效配置、完整关键依赖、每种子聚合诊断；源码变化应使过期表格验证失败。每次输出 train/validation/test 各阶段的空间外质量，并区分原本未知输入与修改导致的空间外输入。

### P1-B：创新的评估与优化目标还不够

当前选择只评估验证集上的频次攻击、逐个特征打分并选前两项；最终报告却评价频次与 n-gram，另有开放 Markov。选择目标与最终威胁覆盖范围不完全一致。两个单项都无收益，也不必然代表联合动作无收益。

修改率只是成本代理，不能当作真实记忆负担。消融仍有旧响应路径：例如 `no_igr` 使用无方向修改，从而同时改变多个因素，尚不能隔离 IGR 的贡献。

**验收目标：**同修改率／同成本对照，单项与联合选择对照，多个预算及独立攻击器评价；消融一次只改变一个因素；报告负结果与不确定性。

### P1-C：扩展真实实验前需处理运行效率

`robustness_protocol.py` 第 419、467 行在遍历每个样本时重复构造整个候选集合。候选扩大到 114,864 后，这种操作随用户数产生大量重复工作。攻击训练与排序也存在可复用结果。

**验收目标：**缓存候选集合、相同训练输入对应的排名；先记录固定规模的耗时和内存再优化。性能优化应保持实验结果一致，并在进入真实数据评估前完成。

## 五、后续总目标

建议将研究问题明确为：

> 在相同用户响应假设和修改成本约束下，能否依据攻击预算选择口令修改建议，使独立测试集上的自适应猜中率下降，并在数据分布变化时保持收益？

这是待验证的问题，不是目前已经成立的创新结论。预算与成本思想是否具备足够新颖性，还需要围绕最终具体算法补充原始文献核查；单纯添加两个权重不足以保证创新。

## 六、按验收门槛推进的任务顺序

### G0：纠正语义与公平性（第一优先级）

1. 修复上述三个反例及同类动作，统一提取、执行、验证语义。
2. 分离建议策略与用户响应；为所有对照采用公平响应能力。
3. 明确论文阈值、距离并列规则、权重、冲突处理与词表差异。
4. 候选覆盖检查贯穿所有阶段；禁止因修改后候选漏收而获得虚假收益。

**交付：**方法定义文档、语义测试、对照协议、人工可核的完整建议链路。

**通过门槛：**已知反例消失；无未标记执行失败；论文与改进版差异可解释；对照只改变预定因素。

### G1：建立一个可信的基线运行

1. 先固定一个场景完成全部诊断，再扩为 Zipf、长尾与头部变化场景。
2. 保存每个种子的样本量、建议数、执行成功率、修改率、空间外比例、猜中率和耗时。
3. 固定代码、依赖、数据和候选哈希；从结果自动生成表格。
4. 将旧协议输出标为历史结果，并同步路线图和技术报告。

**交付：**可以从干净环境重新生成的基线包。

**通过门槛：**第二次运行数字一致；每个结论能定位配置与数据；没有新旧协议混用。

### G2：验证创新是否存在

1. 以公平响应基线开展安全—成本曲线；将修改率约束设为可比较的若干档位。
2. 比较论文顺序、随机／固定顺序、预算选择和联合选择，采用同一动作空间。
3. 在验证集选配置，冻结后使用未参与调参的测试批次；当前已反复查看的测试不能再称作未触碰。
4. 同时评价自适应攻击、不同预算、不同采用率和头部变化。
5. 对正收益报告区间，对零／负收益保留原因诊断。不要通过只保留有利种子或只报头部用户来制造优势。

**交付：**主对照表、安全—成本曲线、消融表、偏移结果和失败案例。

**通过门槛：**至少一个事先明确的主问题得到可重复、可解释的正面证据；同时报告适用范围。若公平修正后仍无收益，停止扩大同一选择器的实验规模，先调整方法假设。

### G3：独立语料与攻击验证

1. MAYA 已有统计迁移可以保留，但增加真正独立的受控策略效果实验。
2. 核对频数来源、站点重叠、划分泄漏、测试规模和使用条件。
3. 选择一个开放攻击器完成严格原始猜测预算评估，再按研究需要扩展。
4. 若作品目标包含论文攻击复现，按论文设置补齐对应 PCFG／OMEN 实验；当前 Markov 替代器应继续明确标注。

**交付：**独立验证报告与复跑配置。

**通过门槛：**独立数据验证支持所声称的适用范围；统计迁移不冒充防御有效性。无需为了“用 AI”而先接大模型。

### G4：竞赛交付

1. 补齐比赛名称、截止日期、评分项与提交规范，建立评分项到证据的映射。
2. 根据真实证据选择最终标题和摘要，明确论文复现、工程实现与自己的贡献。
3. 演示完整链路：语料统计 → 头尾与特征 → 建议及执行状态 → 攻击评估 → 成本与局限。
4. 固定交付版本、依赖和数据获取说明，第二台机器复跑并排练。

**通过门槛：**评委能看懂贡献、复跑主要数字，并区分合成验证与真实结论。

## 七、决策与风险

当前可以继续使用 ZipfGuard 作为参赛基础，但不能沿用“新方法已经提升安全性”的叙述。最值得先解决的研究问题是公平响应下是否仍有预算选择收益。

如果没有，备选方向是面向分布变化的稳健建议，或口令策略评估与错误收益审计。两者都必须重新确定创新点并验证；单独做完工程和审计并不自动满足竞赛创新评分。

不建议此时优先扩大 UI、接入 PassLLM、补更多无关功能。关键依赖链是：**语义正确 → 比较公平 → 可复跑 → 创新证据 → 独立验证 → 交付。**
